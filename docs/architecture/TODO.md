# LibrePaint全面改造TODO

## 目的

この文書は、LibrePaintのコード配置、テスト基盤、描画基盤、描画バックエンド、モバイルUI、コード品質を段階的に刷新するための全プラットフォーム共通ロードマップである。各プラットフォーム固有の実装項目と検証記録は、`docs/<platform>/`の文書で管理する。

ここでいうパッケージングは、C++のクラス、名前空間、ライブラリー、プラグイン、ディレクトリーを責務単位へまとめるコード設計を指す。

## 進行方針

- 各段階は、現状調査、設計記録、実装、移行、退行検査の順で進める。
- 後続段階の調査と試作は先行できるが、本実装は依存する前段階の完了条件を満たしてから統合する。
- R2で現行挙動を固定し、その基準を入力として描画アルゴリズム、実行順序、同期方法の最適化へ進む。
- 新しい生成、検査、計測、ベンチマークの各ツールはNix開発シェルへ固定する。
- 性能改善は計測条件、基準値、変更後の結果を同じ形式で保存し、再現可能な比較を完了条件に含める。
- 大きな設計境界の変更は、実装前に責務、依存方向、移行手順、旧経路の削除条件を設計記録へ残す。

## R1: コードパッケージングの改善

### 目標

名前と実際の責務が一致するコードパッケージを設計し、関連する処理を凝集させる。クラスを探すときに、機能の所有者からディレクトリーとCMakeターゲットを予測できる構造へ移行する。

### 長期構造ビジョン

UIはアプリケーションの利用事例の接続面を呼び出し、起動時の構成責務が
ドメイン実装とI/Oアダプターを登録する構造を目指す。ドメイン処理は、
ファイル、プロセス、ネットワーク、設定、時刻、乱数の各副作用を接続面の外側に分け、
値から値または実行指示を導く計算を独立して構築・検査できる境界へ進める。

このビジョンは各再配置の境界判断に用いる。R1は依存経路の一方向化、具体的な命名、
現存する関心領域ごとのパッケージ分割と集約を先に完了する。ロジック構造の再構築と抽象化は、
新しい所有境界から差し替え、I/O隔離、決定的試験、残る循環の必要性を確認した後に行う。
R1-G6e後半の実装順とYAGNIの適用は
[`document-package-boundary-plan.md`](document-package-boundary-plan.md)を正本とする。

### 実行ゲート

R1は次の順で進め、各ゲートの完了時に停止して成果物と検証結果を確認する。

1. **R1-G1 依存グラフ採取基盤**: CMakeターゲット、種別、定義場所、直接依存を同じ形式で再生成できるようにする。現状採取と再生成を担当し、依存規則はR1-G3とR1-G4が担当する。
2. **R1-G2 公開面と主要クラスの棚卸し**: 公開ヘッダー、主要クラス、プラグインの所有者、利用元、実際の責務を機械可読な台帳へ記録する。
3. **R1-G3 責務地図と依存方針**: アプリケーション、文書、入出力、入力、ツール、キャンバス、描画、リソース、プラグイン基盤の責務と許可依存を定義する。
4. **R1-G4 既存違反基準と継続検査**: 現在の循環、内部ヘッダー参照、逆方向依存を基準化し、許可グラフと診断規則を継続検査へ接続する。
5. **R1-G5 再配置計画**: 新旧ディレクトリー、名前空間、CMakeターゲット、転送ヘッダー、移行順、削除条件を対応表へ固定する。
6. **R1-G6 段階的なターゲット分割**: 特性試験が存在する責務から小さい単位で移動し、各単位で基準表を縮小する。
7. **R1-G7 移行層の削除と文書同期**: 旧経路、転送ヘッダー、一時依存を削除し、責務地図と調査入口を最終状態へ更新する。

## R2: 現行挙動のテスト固定

### 目標

描画最適化で維持する外部挙動、画素結果、実行順序、データ整合性を特性テストとして固定する。意図した仕様と偶然残った挙動を分類し、改造後の互換性を客観的に判定できる基準を作る。

### R2-G1 自由描画ストロークの最小契約

目的は、描画最適化が最初に参照できる小さな画素結果と状態遷移を通常の継続検査へ固定する
ことである。対象は、sRGB 8ビット、500×500画素、単一ペイントレイヤー、固定プリセット、
固定した2入力点、作業スレッド1本による自由描画ストロークとする。Qtの生入力事象から
ツールまでの接続と画面転送は、ストローク実行の契約から原因を分離して判定できるように
後続のR2-G3以降で扱う。

完了条件は次のとおりとする。

- [x] 入力受信からキャンバス表示までの所有者、主要分岐、観測点、不変条件、既存検査を棚卸しする。
- [x] 終了したストロークのレイヤー画素、投影、画像更新通知、待機状態を通常のCTestで検査する。
- [x] 取消し、アンドゥ、リドゥ後のレイヤー画素、投影、待機状態を同じ入力で検査する。
- [x] 基準画像のRGBを完全一致、アルファ値を8ビット値で±3以内とする比較規則を固定する。
- [x] 無効化された旧自由描画検査と、その検査だけが所有した重複画像と未使用プリセットを除去する。

検証階層は、対象CTest、20回の反復実行、画像スケジューラーとストロークキューの関連CTest、
`./scripts/verify-quick`、`./scripts/verify`の順とする。独立実行間で画素結果が変わる場合、
またはRGB差かアルファ値±3を超える差が生じる場合は、基準画像を更新せず、乱数、時刻、
ジョブ順序、色変換のどこで差が生じたかを特定するまで次の契約へ進まない。

### R2-G2 対象試験の構築範囲最適化

目的は、R2の契約追加を全製品・全試験の構築や既存のコンパイラーキャッシュに依存させず、
指定した試験が必要な製品ライブラリーと実行時成果物だけを構築して実行できる状態にする
ことである。現在の試験登録は実行ファイルのリンク依存をCMakeへ伝える一方、`build/bin`から
動的に探索するPaintOp、入出力、QML等の成果物を試験ターゲットの依存として表現しない。
全体構築済みの構築木では不足が隠れ、未構築の木では対象試験以外の構築を追加する運用を
招くため、構築時の依存範囲と実行時の依存範囲を分けて明示する。

対象はmacOSの`tdd-macos`構成、共通の試験登録、`scripts/run-test`、および
`FreehandStrokeContractTest`、`TestInputShortcutMatcher`、`TestToolCoreContract`、
`kis_prescaled_projection_contract_test`を代表とする構築経路である。試験の観測内容、基準画像、
製品の責務境界、アプリケーション束、署名、配布は変更しない。Linuxと他プラットフォームの
実機確認は、macOSで共通の依存表現を確立した後の統合検証へ分ける。

作業順序は次のとおりとする。

1. 代表4試験について、CMake File APIとNinjaの対象別依存グラフ・計画から、直接依存、到達する製品
   ターゲット、生成処理、実行時に探索するプラグイン・QML・試験データを記録する。
2. CMake File APIとNinja計画で直接リンク閉包を検査し、動的探索する成果物だけを既存構築木から
   個別に退避して、対象構築が再生成することを確認する。空の構築木による直接リンク閉包の
   再コンパイルは、同じ依存宣言を重複検査し、構築木パスによるキャッシュ差を測るため完了条件に
   使用しない。
3. 試験を、その検査対象を所有する具体的な製品ターゲットへ直接リンクする。自由描画契約が
   画像・描画・ブラシ用の値だけで成立する場合は、`kritaapplicationui`と
   `KisViewManager`を経由する試験補助処理からUI非依存部分を分離する。
4. 動的探索が必要な試験には、使用する具体的なプラグインまたはQMLモジュールだけをCMakeの
   依存として追加する。`all`、アプリケーション実行形式、全プラグインの集合は依存先にしない。
5. `run-test`は指定ターゲットとその宣言済み依存だけを構築して対応CTestを実行する入口に保つ。
   共通の登録拡張は、同じ実行時依存表現を必要とする現行利用者が複数ある場合だけ導入する。
6. 対象別計画と所要時間を変更前後で比較し、確定した利用方法と保守方法を開発文書へ反映する。

完了条件は次のとおりとする。

- [x] 代表4試験の構築時依存と実行時依存が、所有ターゲットと成果物単位で説明できる。
- [x] macOSの対象別Ninja計画が直接リンク閉包を持ち、退避した動的成果物を対象指定だけで
  再生成して実行できる。
- [x] `FreehandStrokeContractTest`がアプリケーションUIを必要とするかを実装から判定し、不要なら
  画像・描画・ブラシ・資源の具体的な所有者だけへ依存する。
- [x] 必要な動的プラグインまたはQMLモジュールが試験ターゲットから明示的に到達でき、無関係な
  プラグイン、アプリケーション実行形式、全体構築ターゲットへ到達しない。
- [x] 対象構築の前後比較、`run-test`のスクリプト検査、代表4試験、`verify-quick`がmacOSで成功する。
- [x] macOSの全体`verify`は対象範囲の確認後に統合検証として一度だけ成功し、調査中の不足成果物を
  補う手段として使用されない。

対象別構築で必要な製品依存まで削る必要が生じた場合、または製品パッケージの再分割が必要に
なった場合は、この検査段階で構造を変更せず、測定結果と移動元・移動先を持つ独立した構造変更へ
分ける。必要な成果物を具体的なCMakeターゲットで表せない場合は全体構築へ戻さず、その成果物の
所有ターゲットを特定する。依存数が多くても検査対象の実装上必要であることを確認した場合は、
数だけを減らす変更を行わず、根拠と測定値を完了記録へ残す。

### R2-G3 マウス入力からツール呼出しまでの契約
