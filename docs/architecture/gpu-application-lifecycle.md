# GPU文書とアプリケーションの寿命

## 目的と構成

`libs/application/gpu/KisGpuApplicationState.*`は、OSのメモリー通知とQtの
アプリケーション状態を、[共有GPU文書所有者](gpu-document-device.md)へ渡す。
アプリケーション側から文書側へ依存し、画像側はOS通知とGUIの寿命から独立する。

`KisApplication`はGPU文書機能を有効にした構成で共有GPU所有者と通知所有者を保持する。
通知所有者を先に破棄し、文書所有者を後に破棄する。GPUの作成は最初の文書まで遅延する。
`gpuDocuments()`はGUIスレッドで借用する文書所有者を返し、機能無効時は空を返す。
`gpuApplicationState()`は同じ寿命の通知所有者を返し、編集画面が入力による再開と回収を共有する。

## 通知と再開

| 入力 | 処理と結果 |
| --- | --- |
| `ApplicationSuspended` | 全文書の受付済み入力とCPU履歴を維持し、共有GPUを解放する。 |
| `ApplicationActive` | 休止した共有GPUを再作成し、同じ文書モデルの復元を進める。 |
| フォーカス喪失・非表示 | 文書とGPUを維持する。デスクトップの文書切替での再作成費用を避ける。 |
| メモリー通知50〜254 | 現在の下地と作業版を保ち、過去のGPU版を解放する。 |
| メモリー通知255 | CPUの回復値を保ち、全文書のGPU資源を解放する。 |
| メモリー通知0 | アプリケーションが活動中なら再開し、休止中なら次の活動通知を待つ。 |
| GPU喪失 | 全文書を休止し、活動中なら一度再作成を試みる。作成失敗時は次の活動通知・入力で再試行する。 |
| 終了 | 通知の受付と完了回収を止め、共有GPUを解放する。 |

強い圧迫後の新しい入力は、`KisApplication::resumeGpuDocumentsForInput()`で
再開を試み、復元完了後にモデルの新しい編集識別子で継続する。
OSから圧迫解消通知が届かない場合も、次の入力または活動通知が再試行の契機になる。
終了後の再開要求は拒否する。

## 入力とキャンバスの接続

`libs/application/gpu/KisGpuCanvasSession.*`は、同じ文書識別子に属する
入力待ち列と[文書キャンバス](gpu-canvas-rendering.md#文書更新と表示の接続)を保持する。
共有文書所有者、アプリケーション通知所有者、専用ウィンドウは接続所有者より長く保持する。
依存はアプリケーションから文書・描画ツール・表示へ向かう。

`begin()`は入力によるGPU再開を試み、復元完了後に編集を開始する。
`append()`、`replace()`、`commit()`、`cancel()`はCPUの編集識別子を使用し、
受付済み入力と確定要求をGPU交換の前後で保持する。
`setPointerTool()`はマウス・ペンイベントの対象と設定を選択し、同じ入力待ち列へ接続する。
`finishPointerInput()`は受付済みのポインター入力を保ったまま確定を要求する。
`hasPendingInput()`は開始待ちの入力とGPUの確定処理を含み、保存側は完了後の版を取得する。
`setView()`は物理画素への表示変換と、その逆変換に画素比を組み合わせた入力座標を同時に更新する。
不正な変換は両方の値を維持して拒否する。`inputRejected()`は入力側の拒否理由を利用側へ通知する。
同じ文書に複数の表示先を作成でき、編集の同時実行は文書側の一操作契約に従う。
表示先の終了は、その表示先が開始した未確定編集を取消す。

入力・表示の回収は一つのGUIタイマーで進める。受付済み入力、GPU結果の公開、
投影・表示画像・描画・実表示通知の処理待ちは1ms周期で回収し、静止時の文書観測は16msへ戻す。
表示回収の後に入力が新しい版を公開した場合も、次の回収でその版を投影へ渡す。
入力・表示の拒否中は再試行を16msへ戻し、容量回復後に短い周期へ復帰する。
非表示の間も受付済み入力の処理と確定を続け、完了後にタイマーを止める。
表示準備が容量不足で拒否された場合も入力の処理と確定を進め、表示は容量回復後に再試行する。
入力の追加は動作中のタイマーの次回実行を維持し、連続入力による完了回収の延期を防ぐ。
表示・寸法・画素比の通知は保持した画像の再提示を要求する。
回収はアプリケーション通知所有者の`poll()`を使用するため、表示側が先にGPU喪失を
検出した場合も同じ再開規則を適用する。終了後と再作成失敗後の回収は自動再開を伴わない。

共有GPUの直接解放通知はタイマーを止め、表示所有者、入力側のGPU参照の順に解放する。
復元通知後は同じ文書モデルと新しいタイル所有者を取得し、保持した表示条件で描画を再開する。
対象文書の終了通知では入力と表示を解放し、`documentClosed()`を通知する。
他文書の終了は現在の接続を維持する。表示統計は現在のGPUの寿命に属する。

文書が存在する間は16ms間隔で非同期文書処理とGPU喪失を回収する。
これは文書復元の進行用であり、描画側の入力処理・表示同期はそれぞれの所有者が担当する。
文書が空、GPU休止中、再作成失敗後と終了後は回収タイマーを停止する。
最後の文書の終了は共有GPUも解放する。

## GPU文書の編集画面

`plugins/extensions/gpucanvas/KisGpuDocumentWindow.*`は、一つの登録済み文書の編集画面を所有する。
専用のQtウィンドウを表示領域へ埋め込み、描画セッションにマウス・ペン入力と表示を渡す。
画面の大きさと画素比から文書全体を収める座標変換を求め、入力にも同じ変換を使う。
色・直径・消しゴム・対象レイヤーの変更は次の入力設定へ渡す。
レイヤー追加とUndo/Redoは文書の既存操作を使用する。

構築成功後の画面は、その文書を閉じる責任を持つ。共有文書所有者とアプリケーション通知所有者は
画面より長く保持する。画面の終了は入力・表示セッションを解放してから対象文書を閉じ、
別文書のGPU寿命を維持する。外部からの文書終了は画面を閉じて入力を切り離す。
`kritagpucanvaswindow`は具体的な描画セッションとQt Widgetsへ依存する。

保存要求は進行中のポインター入力を確定し、文書が操作可能になってから通知する。
画面はCPUの回復版の変化を弱い参照で観察し、GPU画像や過去の回復画素を追加保持せずに
変更番号を更新する。保存完了は取得した変更番号と現在の版が一致する場合に未保存状態を解除する。
保存中の新しい編集は未保存状態を維持する。未保存の画面を閉じる操作は保存・破棄・取消しを選択し、
保存を選んだ場合は現在の版の保存成功後に閉じる。

## GPU文書の作成・保存・再読込

`plugins/extensions/gpucanvas/KisGpuCanvasWorkspace.*`は編集画面の一覧とKRA処理を所有する。
共有文書・通知所有者を借用し、画面とファイル処理から具体的な文書所有者へ依存する。
新規作成は登録済み文書へ描画レイヤーを追加する。読込は登録済みの空の文書へ
[KRA読込](gpu-kra-load.md)の回復値を復元し、成功後に画面を公開する。
取消し・失敗・読込中の画面所有者の終了は未公開文書を閉じ、最後の文書なら共有GPUを解放する。

保存は現在の版と文書情報を固定し、[KRA保存](gpu-kra-save.md)をGUIタイマーで進める。
成功時は保存済みKRAの`documentinfo.xml`を同じ64 MiBのCPU上限内で取得し、
標準保存処理が更新した作者・日時・編集回数を次回の保存へ渡す。
情報の取得失敗は画面に示し、保存済みファイルの再読込後に次の保存を受け付ける。
GPU解放時は画素読取り中の保存を中断し、再開後の再保存を受け付ける。
CPUへ取得済みの保存はGPUの寿命から独立して完了する。

画面の親が閉じる際は各文書の未保存確認を行い、取消された親画面を維持する。
アプリケーション終了時は文書所有者の寿命内で編集画面と保存処理を解放する。

`plugins/extensions/gpucanvas/KisGpuCanvasExtension.cpp`は標準の画面プラグインとして
主画面の操作管理へ新規作成とKRA読込を登録し、作成・保存所有者を保持する。
`krita/krita5.xmlgui`の「Tools → GPU Canvas」から呼び出す。
新規作成は1024×1024のRGBA8 sRGB文書を開き、保存は編集画面の操作から実行する。
GPU文書機能を有効にしたmacOS・Linux構成で利用する。
画面・保存・メニューはプラグイン側から具体的なアプリケーション所有者へ依存し、
標準アプリケーション所有者は画面プラグインへ依存しない。

プラグインとの境界で共有するQtの所有者・画面は、次のライブラリーが公開する。
各クラスの型情報と通知定義を一つの実体から利用し、借用したQObjectの型識別と
画面からの描画セッション取得を同じ契約に揃える。

| 定義の所有ファイル | 公開するライブラリー |
| --- | --- |
| `libs/document/gpu/KisGpuDocumentDevice.*` | `kritadocumentgpudevice` |
| `libs/application/gpu/KisGpuApplicationState.*` | `kritaapplicationgpustate` |
| `libs/application/gpu/KisGpuCanvasSession.*` | `kritaapplicationgpucanvas` |
| `plugins/extensions/gpucanvas/KisGpuDocumentWindow.*` | `kritagpucanvaswindow` |

デスクトップ構成は共有ライブラリーと生成した公開宣言を使用し、製品とともに配置する。
iOS構成は共通の`kis_add_library`が定める静的配置を使用する。

## OSとの接続

- Appleプラットフォームはメインキュー上の`DISPATCH_SOURCE_TYPE_MEMORYPRESSURE`を使用し、
  NORMALを0、WARNを50、CRITICALを255へ変換する。
- LinuxでQt DBusを利用する構成は、システムバスの
  `org.freedesktop.LowMemoryMonitor`、`/org/freedesktop/LowMemoryMonitor`から
  同名インターフェイスの`LowMemoryWarning(y)`を受け取る。
- Windowsは`LowMemoryResourceNotification`を`QWinEventNotifier`で受け取り、履歴を解放する。
  圧迫が継続する間の連続通知は一秒ごとに回収する。

ネイティブ通知の監視は終了または通知所有者の破棄時に解除する。
プラットフォームの通知が利用できるかどうかにかかわらず、Qtの休止・活動・終了通知と
GPU割当の拒否は同じ文書契約を使用する。通知によるGPU解放に画素読取りを追加しない。

## 検証と保守

`KisGpuApplicationStateTest`はQtアプリケーション通知の接続、履歴解放、
受付済み入力を保持した休止、活動通知・入力による再開、GPU喪失と終了を検査する。
所有者のGPU再作成と非同期復元には実GPUを使用する。
`KisGpuCanvasSessionTest`は実ウィンドウと複数文書を接続し、GPU交換を挟む入力の画像、
複数表示先、非表示中の確定、表示面の再作成、GPU喪失、文書終了と所有する編集の取消しを検査する。
OS全体へのメモリー圧迫は起こさず、通知された値を同じ受付口へ渡して文書への効果を検査する。
`KisGpuDocumentWindowTest`は実際の編集画面で入力、レイヤー追加とUndo/Redoを操作し、
画素転送0、保存前の入力確定、保存中の変更の保持、終了取消し、
対象文書だけの終了と外部からの文書終了による画面の切離しを検査する。
`KisGpuCanvasWorkspaceTest`は固定版の保存・再読込、連続保存の編集回数、
GPU解放後の再保存、読込失敗と所有者終了時の未公開文書の回収を検査する。
`KisGpuCanvasEntryTest`は実際の`KisApplication`と登録プラグインを使用し、
旧方式の画像が空の主画面からメニュー操作でGPU文書を作成する。
共有所有者の利用、GPU休止・復元後の同じ文書と親画面終了時の解放を検査する。
借用するQt所有者の型識別と、プラグインが作成した画面からの描画セッション取得も検査する。
Linuxの通知接続は、専用D-Busのアドレスを`DBUS_SYSTEM_BUS_ADDRESS`に設定し、
`KIS_GPU_TEST_ISOLATED_BUS=1`で同じテストを実行する。テストが専用バス上で
通知サービスを登録し、実際の`LowMemoryWarning(y)`による休止と再開を検査する。
構築・実GPU検査は[開発手順](DEVELOPMENT.md#gpu文書タイルの検証)に従う。
