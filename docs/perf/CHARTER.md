# 描画性能の要件（CHARTER）

この文書は、LibrePaint の描画性能の改善（Issue #108）について、目的、判定方法、判断の規則を定める。利用者が管理する。エージェントはこの文書を変更しない。作業項目と判断は、この文書の条文に照らして決める。

## 目的

実機で、ペン入力から画面表示までの遅延を短くする。最初に表示経路の遅延を解消し、その後で高負荷（大きなキャンバス、多いレイヤー、大きなブラシ）の描画性能を上げる。

UI と操作の見かけは旧版から変えない。Undo の範囲、単位、上限の設定も旧版と同じにし、履歴を区切る操作は作らない。保存結果の画素は旧版と 8bit 換算で1階調以内に収め、画素以外の内容は完全に一致させる。

## 主指標と計測

主指標は、入力から表示までの時間（中央値と P95）とする。ホバー中のブラシ輪郭と、描画中のインクを分けて測る。

- 区間ごとの内訳も記録する。区間は、OS からの入力の受信、輪郭の更新要求とストローク処理、キャンバス描画の開始と終了、画面への受け渡し、表示。
- 表示の時刻は、Windows では PresentMon で測る。
- ペンの検出から OS の受信まで、およびパネルの応答は、ハイスピードカメラで定期的に確認する。
- 比較は、同じ機器で、合成ペン入力による同じ軌跡で行う。中央値の変動が5%未満になるまで測り直す。

基準機は Surface Pro 7（Windows、60Hz）とする。フェーズL3 から Mac（M2）と iPad を加える。

## 暫定の確定事項

利用者だけが見直せる。

1. 画素の正本を GPU に置かない。正本は CPU（KisPaintDevice）に置き、GPU には速くしたい処理のための写しだけを置く。
   - 理由：調べた範囲では、機能の多い主要な編集ソフトは CPU 正本である。GPU 正本は、機能を絞ったタブレット向けの編集ソフトだけだった。CPU 正本なら、保存、フィルター、テキスト、プラグイン、Undo が旧版の仕組みのまま動き、GPU を失ってもデータは失われない。
2. 軽負荷のペン応答性は、表示経路の改善から着手する。
   - 理由：2026-11-06 の Surface での実測で、遅れの大半が画面への受け渡しから表示までの待ちで、ブラシ計算は約7ms だった（Issue #108「背景」）。

## 要件から外すもの

他の編集系クリエイティブソフトで一般的ではない保証は、要件に入れない。

- GPU を失ったときに、編集を失わずに続けること。致命的なエラーとして通知し、最後の自動保存から復旧できればよい。
  - 理由：確定済み操作の保持と再生が必要になり、機能ごとの再生の一致、保持量の上限による描画の拒否、派生する状態の作り方の管理という費用を生む。多くの編集ソフトも、最後の保存以降の編集は失われる。
- CPU とのビット単位の一致。1階調以内の差を許す。
- 全機能の GPU 化。計測で効果が示された処理だけを GPU で行う。
- CMYK・Lab・Gray・アニメーションの GPU 化。

## 判断の規則

- 文書のデータモデル、履歴、障害時の復旧、精度と一致、保存形式、拡張の境界、スレッドと同期の構造のように、波及範囲の大きい判断を決める前には、先行研究と他ソフトの扱いを調べる。結果は DECISIONS.md に書く。一般的な水準を超えて作り込むのは、主指標の計測で必要と示された場合だけにする。
- この文書の条文と主指標に反しない限り、エージェントが自分で決める。利用者には確認しない。判断は [`DECISIONS.md`](DECISIONS.md) に「日付、判断、理由、関係する指標」の形で1行ずつ追記する。
- 作業項目には、改善する指標、または満たす条文を書く。どちらも書けない作業は行わない。
- 案を選ぶ優先順位は、主指標の改善、コード量が少ないこと、旧版の挙動に近いこと、の順とする。

## 停止条件

次の場合は作業を止め、分析を Issue #108 の「停止の記録」に1行で書いて、利用者の判断を待つ。

- 変更によって、いずれかの環境で主指標が悪化し、原因を直せない。
- フェーズG の GPU レイヤー合成の後も、高負荷で旧版の 0.8倍より速くならない。または、軽負荷が悪化する。
- この文書の条文を満たせないことが分かった。
