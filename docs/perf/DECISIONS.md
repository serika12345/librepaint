| 2026-11-06 | 画素の正本を GPU に置かない（利用者の暫定確定） | 機能の多い編集ソフトは CPU 正本。GPU 正本は CPU 経由の互換コード（約1.7万行）、文書単位のエンジン切り替え、Undo 履歴の区切りを必要とした | 全体 |

| 2026-11-06 | 軽負荷のペン応答性は、表示経路の遅延の解消から着手する | Surface Pro 7 の実測で、入力から表示まで中央値 56.8ms のうち 43.8ms が画面への受け渡しから表示までの待ちで、ブラシ計算は約7ms だった | ホバー輪郭・インクの入力から表示まで |

| 2026-11-07 | OS をまたぐ比較は、合成入力の軌跡を再生しながら画面を取り込み、画面に出た輪郭とインクの位置から遅れを求める方式で行う。各 OS で最小の描画アプリも測り、差で比べる | PresentMon は Windows にしかない。Windows では同じ回の PresentMon による値と中央値が 2ms 以内で一致し、表示方式も変わらなかった | ホバー輪郭・インクの入力から表示まで |

| 2026-11-07 | #108 の「GPU が描き始めるまで 32.5ms」は PresentMon の MsGPULatency（フレームの CPU 処理の開始が起点）であり、present の呼び出しからは約 16ms と読む | 起点の取り違え。present から GPU の完了まで 32.3ms、表示まで 43.8ms | 画面への受け渡しから表示まで（Windows） |
| 2026-11-07 | Linux の LibrePaint の遅れの主因は Qt 6.11.1 の GLX 実装（QGLXContext::makeCurrent が同じ窓に垂直同期の設定を再適用しない、QTBUG-147854）と判断する。対処は L3 で Qt を修正入りの版（6.11.3 以降、qtbase 9106893dce32）にすること | 同じ Mesa・同じ窓の大きさで、交換が毎フレーム 15ms 止まり、設定を毎回再適用すると LibrePaint は 75.3/61.3ms から 45.9/48.3ms（取り込みの値）になり、公式 Krita（Qt 6.12.0、56.2/56.4ms）より速くなった | ホバー輪郭・インク（Linux） |
| 2026-11-07 | macOS の取り込みの値は補正せずに表示までの時間として使う | Metal の参照アプリで presentedTime と突き合わせると、取り込みの時刻との差は +0.5ms だった | ホバー輪郭・インク（macOS） |
| 2026-11-07 | macOS 版 1.0.3 が文書を開くと落ちる原因は Qt 6.11.1 の QImage::toCGImage（QTBUG-147602、6.11.2 で修正）と判断する。対処は L3 で Qt を修正入りの版にすること | 待機カーソルの画像（iCCP 付き PNG）の変換で解放済みの色空間を使う。画像の iCCP チャンクを無効にしたコピーでは落ちなかった | 全体（macOS） |
| 2026-11-07 | macOS では LibrePaint の表示経路の改善を急がない | 同じ画面と窓の大きさで、LibrePaint（21.5/23.3ms）は最小の Cocoa アプリ（26.8/27.5ms）と同程度で、公式 Krita（30.1/45.2ms）より速かった | ホバー輪郭・インク（macOS） |
| 2026-11-08 | 色プロファイルの登録から PQ プロファイルを探した結果を覚えておき、プロファイルの追加・削除で捨てる | Wayland では参照画像の装飾が描画のたびに p2020PQProfile() を呼び、全プロファイルのガンマ推定で 1 回約 10ms かかっていた（c34d4d1a16 で名前の検索から条件の検索に変えたため）。変更後、描画は 10.7ms から 0.5ms になり、取り込みの値はホバー 53.5→35.9ms、インク 56.1→31.5ms で公式 Krita（37.6/33.1ms）と同程度になった | ホバー輪郭・インク（Linux Wayland） |
