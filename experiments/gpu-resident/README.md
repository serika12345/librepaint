# GPU 常駐文書の最小比較実験

CPU に文書画素を保持する方式と、GPU に保持してブラシ計算から表示までを続ける方式の
性能と画素結果を比較する独立した PoC。[Issue 87](https://github.com/serika12345/librepaint/issues/87)
に関連する設計判断の材料として、同じ描画規則、タイル配置、入力列を三方式で実行する。

## 比較する構成

| モード | 文書の正本 | ブラシ生成・画素合成 | レイヤー合成 | 更新時の CPU → GPU 入力 |
| --- | --- | --- | --- | --- |
| `cpu` | CPU | CPU | CPU | 変更された合成済みタイル |
| `hybrid` | CPU | CPU | GPU | 変更された文書タイルと合成命令 |
| `gpu` | GPU | GPU | GPU | 座標、半径、色、筆圧相当の不透明度、タイル別命令 |

三方式の表示は同じ wgpu-native の描画処理を使う。macOS は Metal、他の対応ホストは
Vulkan を選択する。ソフトウェア GPU は検証対象から除外し、取得時にエラーにする。
今回の実測対象は macOS の Metal 経路。OS 別の製品接続は別の検証範囲となる。

CPU 方式は現行製品の「CPU 文書・ブラシ・投影、GPU 表示」という責務配置を最小化した
再実装である。製品のブラシ、OpenGL、Qt、ストロークキューを含めないため、
得られた倍率は LibrePaint 製品全体の高速化率を表さない。

## 構成

| ファイル | 責務 |
| --- | --- |
| `model.h`、`model.cpp` | 整数画素規則、固定入力列、疎なタイル配置、領域別の候補抽出、CPU 並列処理 |
| `engine.wgsl` | GPU 上のブラシ生成、入力順の描画、レイヤー合成 |
| `display.wgsl` | 合成済みタイルから表示用画像を生成 |
| `gpu.h`、`gpu.cpp` | GPU 資源、部分転送、描画発行、完了観測、履歴コピー、検証用読み戻し |
| `main.cpp` | 三方式の実行、操作契約、計時、最終画像検証、JSON 出力 |
| `pixel_contract.cpp` | 手計算した通常合成とブラシ被覆率の基準値 |
| `run.py` | 固定 Nix 依存による構築、順番を巡回する比較、原記録と統計の出力 |
| `CMakeLists.txt` | 製品ライブラリーから独立した構築・CTest |

実行手順は開発マニュアルの
[GPU 常駐文書の最小比較実験](../../docs/architecture/DEVELOPMENT.md#gpu-常駐文書の最小比較実験)
が所有する。構築の直接依存は C++ 標準ライブラリー、スレッド、wgpu-native。
比較実行ファイルの空構築は 5 工程、画素契約を含む全対象は 7 工程である。

## 画素と操作の契約

- 文書は正方形、タイルは 64×64、RGBA8 のアルファ乗算済み画素。R が整数の下位バイト。
- 合成は符号化されたチャンネル値に対する通常合成。各段階で整数丸めを行う。
- ブラシの被覆率は `max(0, radius² - distance²) / radius²`。整数ピクセル位置を使用する。
- 色と不透明度を変えたブラシ印を順番に処理する。同じ画素の描画順序を全方式で維持する。
- CPU は継続利用する作業スレッドへ重複しないタイルを分配する。Release の `-O3` を使う。
- GPU はタイルごとの候補列を受け取り、各画素について候補を入力順に処理する。
- 下地レイヤーは異なる色・透明度の固定画素。重なる中央領域だけにタイルを持つ。
- 描画対象は最上位レイヤー。表示では下から順番に合成する。
- 図形編集は楕円の拡大操作。毎回開始前の画素へ戻し、新しい形を描く。
  更新範囲は変更前後の形状の和集合とする。
- 最終の作業結果を保持することを確定とする。開始前のコピーへの復元で取消しと一段の
  Undo を検査し、保持した命令列の再実行で Redo を検査する。

タイルは固定入力列で必要となる場所を初期化時に予約する。動的割当やメモリー不足時の
退避費用を混ぜず、画素の所有場所と処理場所を比較するための固定容量モデルである。
図形変更時には作業対象レイヤーの予約済み領域全体を復元する。この GPU 内コピーも
計測対象に含める。Undo 履歴は一段とし、長期間の履歴管理は製品設計の対象とする。

線形光での合成、色管理、高ビット深度、混色・にじみ、選択範囲、消しゴム、フィルター、
保存、デバイス喪失、メモリー退避は、この比較から意図的に除外する。
転送と実行場所の影響を少量の同一計算で切り分けるためであり、製品への採用には
それぞれの契約と費用を追加して検証する。

## 測定条件

各試行は 24 更新。通常描画は一更新に 4 個、図形編集は一更新に 64 個のブラシ印を渡す。
入力は固定式で生成し、乱数を使用しない。可変径は半径の 6/8、7/8、8/8 を巡回する。

| 条件 | 文書 | レイヤー | ブラシ直径 | 下地レイヤーの占有領域 |
| --- | --- | ---: | ---: | --- |
| `light` | 1024×1024 | 1 | 32 | 下地なし |
| `heavy` | 4096×4096 | 24 | 512 | 中央 1024×1024 |
| `varying` | 4096×4096 | 24 | 512 を基準に変更 | 中央 1024×1024 |
| `shape` | 4096×4096 | 24 | 96 | 中央 1024×1024 |

すべてのレイヤーが 4K 全面に画素を持つ負荷とは区別する。
表示用画像は文書と同じ解像度で全体を描く。変更領域の合成と転送はタイル単位。

計測開始は入力列の処理開始、終了は最後の表示用画像の GPU 完了を CPU が観測した時点。
候補抽出、CPU 処理、転送、GPU 命令構築、描画、完了待ちを含む。
初期化、シェーダー作成、初期画素転送、CPU 基準画像の作成、試行間の状態リセット、
最終画素の読み戻しと照合は区間外に置く。各プロセスで 2 試行を準備に使う。

`--in-flight 1` は各更新の完了を待つ応答時間の比較、`3` は最大三更新分を送信する
処理量の比較。後者の総時間を個々の入力遅延として扱わない。
完了は非同期ポーリングと 50 µs の休止で観測し、その観測遅延を両方式の時間へ含める。
`paced` は更新開始を 4 ms 間隔で予定し、実際の最終入力から完了までの残り時間も記録する。

CPU 実働は同じ計測区間内のプロセス全スレッドの合計。
`mean_frame_host_stages_wall_ms` は候補抽出、CPU 描画、CPU 合成、GPU 発行の順の
ホスト経過時間であり、全スレッド CPU 実働とは別の値。
GPU のブラシ・合成・表示時刻は `profile` の別プロセスで測る。
GPU 時刻の読み出しは処理と同期を追加するため、その総時間を速度比較へ混ぜない。

画素転送量はアプリが API に渡した論理バイト数。GPU 内コピーと命令転送は別に記録する。
Apple Silicon の共有メモリー上でも、API 上のコピー費用と GPU が画素を読む帯域は存在する。
画素転送 0 はメモリーアクセス 0 を意味しない。

## 検証と結果の扱い

CTest は手計算の画素規則、描画、楕円編集、キャンバス端の切り詰め、取消し／Undo、Redo を
三方式で検査する。各更新の文書、投影、実際の描画先画像を CPU の単一スレッド基準へ
全画素で完全一致させる。性能測定でも最終文書・投影のハッシュ一致と表示の全画素一致を
要求する。GPU 常駐の計測区間に画素転送があれば失敗する。

`run.py` はソース、実行ファイル、wgpu ライブラリーの SHA-256、コンパイラー、固定依存版、
全試行値、中央値、P95、プロセス別中央値を保存する。方式の順番は反復ごとに巡回する。
CPU スレッド数は 1、4、8 の対照で評価し、小負荷での並列化費用を含めて解釈する。

公開用の測定要約は [results.json](results.json)。原記録と環境識別情報は実行時に指定した
出力先へ保存する。結果を更新する場合は、同一実行ファイルの比較一式を用い、
条件、画素一致、反復数、中央値と P95 を一緒に更新する。

### 基準測定

`results.json` の基準測定は 156 プロセス、準備試行を除く 1,296 入力列。
速度比較 1,224 列と GPU 区間分析 72 列を分ける。全試行で最終画像の照合に成功した。
次表は CPU 4 作業スレッド、一更新ごとの GPU 完了待ち、入力待ちなしの比較。
各条件は 3 プロセス×12 入力列で、値は 24 更新全体の中央値／P95、単位は ms。

| 条件 | CPU 文書・CPU 合成 | CPU 文書・GPU 合成 | GPU 常駐 |
| --- | ---: | ---: | ---: |
| 小負荷 | 8.65 / 11.11 | 9.51 / 11.08 | 9.27 / 10.42 |
| 高負荷 | 117.98 / 130.38 | 72.26 / 129.92 | 44.06 / 45.21 |
| 可変径 | 90.54 / 99.34 | 62.59 / 68.27 | 40.61 / 46.69 |
| 楕円編集 | 117.80 / 135.34 | 67.18 / 73.21 | 47.23 / 51.45 |

高負荷の一更新の完了時間は、CPU 方式が中央値 4.86 ms、P95 6.13 ms、GPU 常駐が
中央値 1.83 ms、P95 1.98 ms。CPU 実働合計は入力列あたり 281.75→6.56 ms。
画素アップロードは 33.42 MiB→0、GPU 常駐の命令転送は約 67.55 KiB。
初期転送、測定後の照合用読み戻し、GPU 内メモリーアクセスは別に扱う。

CPU 作業スレッドを 8 本にした別対照では、高負荷の CPU 方式は 96.63 ms、
CPU 描画・GPU 合成は 66.89 ms。CPU ブラシのループは今回のコンパイラーが自動ベクトル化を
選択せず、レイヤー合成のループは幅 4 でベクトル化した。専用 SIMD ブラシ実装の性能を
代表する結果ではない。

4 ms 間隔の入力では、24 更新の予定入力時間だけで 92 ms になる。高負荷の全体中央値は
CPU 113.85 ms、GPU 常駐 95.08 ms、実際の最終入力から完了までの中央値は
それぞれ 3.96 ms、2.66 ms。小負荷は全方式で約 94 ms となる。

この条件では GPU 常駐が高負荷と形状更新を改善し、小負荷では CPU 方式がわずかに速い。
中間方式の高負荷には遅い試行があり、中央値だけで応答時間を評価せず P95 と原試行値を併用する。
GPU 区間分析では 4K 表示用画像の描画費用がブラシ計算より大きく、表示解像度・可視範囲も
後続の性能評価対象となる。

この PoC の合格は、固定条件の GPU 常駐描画が成立し、画素結果と編集操作が一致し、
転送量・CPU 消費・完了時間を再現可能に比較できること。性能の優劣は負荷ごとに判定する。
次の設計判断は、実表示の同期、下地を読むブラシ、タイルの動的割当・退避、保存・回復を
追加した際にも GPU 常駐の利点を維持できるかで行う。
