# 無人ループ反復：Issue #89

あなたは無人ループの1反復を実行する。利用者は応答しない。質問・承認待ち・提案だけで終わることは失敗とみなす。
この反復で必ず実装を前進させ、コミットして push してから終了する。

## 目標

LibrePaint 全体を既定で新エンジンの文書で動かす（Issue #89 / 親 #87）。対象は #107 の移行範囲に限る。
製品要件・運用規則・移行範囲は **Issue #107（利用者管理）** に従い、#89 や子 Issue と衝突する場合は #107 を優先する。
バックログの上位のフェーズから処理する。フェーズ0（負債回収）が残っていればそれを先に、次に **フェーズA**：
#107 の GPU 常駐の範囲を実装し、それ以外は CPU 経由で動くことを確認する。
品質磨き・性能・macOS/Metal・環境間一致（#91）・旧経路の撤去はフェーズBで行う。

## 手順

1. `AGENTS.md` を読む。`gh issue view 107` を読む。`gh issue view 89` で「ループ運用状態」と「全体稼働バックログ」を読む。
2. 作業ツリーに未コミット変更があれば、それを最初に仕上げてコミットする（前反復の途中作業）。
3. 最新の全体 verify 要約に失敗があれば、それを今回の最優先項目にする（修正、または下記の隔離）。
4. それ以外はバックログの未完了項目のうち最上位を選ぶ。大きすぎる場合はこの反復で終わる大きさに分割し、
   分割結果をバックログへ書き戻してから先頭を実装する。
5. 実装する。ラフでよい。動作する通常経路を広げることを、細部の完成度より優先する。
6. 増分ビルドと、変更に直結する局所試験で確認する：
   `build-incremental native build <target>`、`run-test <target> [regex]`。
   変更が広い場合は `verify-quick` も実行する。全体 `verify` はループ駆動が定期実行するので、自分では実行しない。
7. 論理単位ごとにコミットし、`git push origin HEAD:feature/issue-89-gpu-engine-rewrite` する。
8. Issue #89 本文を更新する（下記の規則）。
9. 時間の目安は1反復あたり90分。超えそうなら途中でもコミット・push・Issue 更新をして終了する。

## 進め方の規則

- 阻害（macOS 実機、外部依存、判断不能）に当たったら、Issue の「阻害」に1行記録して別の項目へ移る。止まらない。
- 5分以上かかる、または不安定な既存試験は、原因を短時間で直せなければ
  `QSKIP("LOOP-DEFERRED: <理由>")` で隔離し、Issue の「隔離した試験」に列挙する。期待値が古いだけの試験は直す。
- 画素の比較は #107 の基準（8bit 換算で1階調以内、画素以外は完全一致）で行う。CPU とのビット一致を求める試験は作らない。
- 試験は1つの変更につき通常経路1つと境界1つまで。2,000行を超える試験ファイルには追加しない。
- 次の仕組みは作らない（フェーズ0で撤去した）：確定済み操作の保持と再生による画素の再構築、
  デバイス差し替えによる無損失の継続、CPU とビット一致させるための模倣・事前計算表・CPU 側の複製計算。
  履歴はタイルの版の切替えで、GPU 喪失は最後の自動保存からの復旧で扱う（#89「採用する設計」）。
- 進捗指標は網羅スモークの結果（GPU / CPU経由 / 失敗 の件数）。存在すれば反復ごとに実行し、Issue に件数を記録する。
- 長時間コマンドには `timeout` を付ける。バックグラウンドに放置したプロセスを残さない。
- 禁止：force push、master や他ブランチへの push、履歴の書き換え、`build/agent-loop/` の削除、
  `scripts/agent-loop/` の無効化、Issue #107 の編集。
- `build/agent-loop/DONE` は、#89 のバックログに阻害なしで着手できる未完了項目が残っておらず、
  全体 verify が成功した時にだけ作成する。阻害で残った項目は Issue の「阻害」に列挙しておく。

## Issue 本文の更新規則

- **更新の直前に `gh issue view 89 --json body` で最新の本文を取得し、変更する行だけを置き換えてから
  `gh issue edit 89 --body-file` で書き込む。** 反復の開始時に読んだ本文を書き戻さない。
- バックログ先頭の「必読：#107」の行は削除しない。
- 「ループ運用状態」節は10行以内。現在版、直近の成果、網羅スモークの件数、最新の verify 結果、阻害だけを書く。
- 試験の件数・秒数などの詳細はコミットメッセージに書き、Issue 本文には書かない。
- バックログ項目は完了したら `[x]` にし、新しく分かった作業は適切な位置へ追加する。完了した項目は
  10件を超えたら古い順に削除してよい（履歴は git にある）。
- 「目的」以下の設計節は、設計を変えた場合だけ短く更新する。
